# ADR 0017: 100 プロジェクト超での状態一覧・issue_get の要約形式・キー形式の明記

- 状態: 採用(2026-11-02。GitHub issue #4「動作確認のフィードバック(2)」への対応)
- 関連: ADR 0004(キーの形式)、ADR 0007(応答サイズ)、ADR 0012(未完了の状態)、ADR 0016(状態一覧のキャッシュと上限 100、issue_list の `detail`。**本 ADR が上限と書き込みの回数を更新する**)

## 背景

参加プロジェクトが 142 件のスペースでの動作確認で、次の点が報告された(確認は ADR 0016 の前のコミット)。

1. ADR 0016 の上限 100 でも、142 プロジェクトでは `my_tasks` が `status_projects_truncated` になり、`issue_list` の `status_id=not-closed`(プロジェクト指定なし)は `argument_error` になる。
   - 実際に漏れうる範囲は「上限外のプロジェクト **かつ** カスタムの未完了状態」の課題だけ。既定の状態(未対応・処理中・処理済み)はどのプロジェクトにもあるため、取得できた分の和集合に必ず入る。
   - ADR 0016 の 100 は #2 の「数十件」から判断で置いた数で、根拠が弱かった。
2. `issue_get` は Backlog の生データを返し、担当者・作成者・更新者ごとに `nulabAccount` を含むユーザー情報が付いて重い。
3. 応答サイズの上限ガードは期待どおり(報告のみ。対応しない)。
4. キーの形式が、生データ(camelCase)と加工した出力(snake_case)で違う。ADR 0004 どおりだが、説明がない。

## 決定

### 1. 状態一覧を引くプロジェクト数の上限を 200 にし、キャッシュを途中でも保存する

- 上限を**実時間から逆算**して決める。前提(**仮定**。V17 で実測する):
  - Workers から Backlog への 1 回の往復は 150〜200 ミリ秒程度。
  - MCP クライアントのツール呼び出しのタイムアウトは 60 秒程度(クライアントごとに違い、未確認)。
  - 状態一覧の取得に使えるのは 40 秒程度(ほかに課題の取得が最大 30 ページある)。40 秒 ÷ 0.2 秒 = **200**。
- 定数を 2 つに分ける:
  - `MAX_STATUS_PROJECTS` = **200**。`my_tasks` と、`issue_list` のプロジェクト指定なしの `not-closed`(参加プロジェクト全件が対象)に使う。超えたときの振る舞い(truncated + warning / `argument_error`)は変えない。
  - `MAX_STATUS_PROJECT_KEYS` = **100**(据え置き)。`issue_list` で `project_key` / `project_keys` を明示したときの上限。こちらは GetProject も N 回増えるため。
- **キャッシュの書き込みを途中でも行う**(ADR 0016 の「書き込みは最大 1 回」を緩める):
  - Backlog から新しく引いたプロジェクトが **20 件たまるごと**に `flush` し、最後にも `flush` する。途中で失敗しても、引けた分は `finally` で `flush` する(`my_tasks` も `issue_list` も同じ)。
  - 理由: キャッシュが空で数が多いと、初回の呼び出しがクライアントのタイムアウトで切られうる。切断されると、それまでの処理は中断されうる(Cloudflare の docs。`ctx.waitUntil` に渡さない限り)。最後にまとめて書く方式だと KV が温まらず、次回も同じところで切られる。途中で書けば、次回は続きから引ける。
  - KV の読み取りは 1 回のまま。書き込みは最大 ⌈200 / 20⌉ + 1 = 11 回で、subrequest の上限(有料プラン 10,000)に対して無視できる。
- 呼び出し回数(キャッシュが空の最悪ケース):
  - `my_tasks`: GetMyself 1 + プロジェクト一覧 1 + 状態一覧 200 + overdue / upcoming / watching 各 10 ページ = **232**。
  - `issue_list`: 指定なしはプロジェクト一覧 1 + 状態一覧 200 + GetMyself 1 + 子の収集 2 + 一覧 1 = **205**。指定ありは GetProject 100 + 1 + 状態一覧 100 + 2 + 1 = 204。`maxApiCalls` は大きい方の **205**。

### 2. issue_get に `detail`(`full` / `summary`)を足す

- 省略時は **`full`**(生データ。logvalet 互換)。
- `summary` は `issue_list` の summary と**同じ 13 項目 + `description`(全文)**。ユーザーは名前だけになる。マッパーは `issue_list` と共有する。
  - 出力は `issue_list` の summary と同じく `analysisEnvelope`(resource `issue_get`)にし、`analysis` は `{ issue: {...} }`。
- 「`nulabAccount` だけを省く」引数は足さない。引数が増えるだけで、`summary` との使い分けが曖昧になる。
- 引数の追加は logvalet の baseline との差分なので、`test/helpers/baseline.ts` に理由つきで足す。

### 3. キーの形式を README に明記する

- README に 1 段落を足す: Backlog の生データ(`issue_get` / `issue_list` の `full` など)は camelCase、Logbutler が加工した出力(分析系・`user_me`・`search`・`detail=summary`)は snake_case(ADR 0004)。
- `issue_get` / `issue_list` の `detail` 引数の説明に「summary は snake_case」と書く。
- 87 個すべてのツールの説明は変えない(baseline の差分が大きくなる割に、得るものが少ない)。MCP サーバーの `instructions` は今は使っていないので、足さない。

## 却下した案・将来の経路

- **`my_tasks` は、担当・ウォッチしている課題があるプロジェクトだけ状態一覧を引く**(issue #4 の案)。
  - `issue_list` のプロジェクト指定なしには効かない(全プロジェクト・全担当者の問い合わせで、絞る材料がない)ので、上限の引き上げ自体は避けられない。
  - 状態を決めるためではなく、引くプロジェクトを選ぶための偵察にだけ使うなら、ADR 0012 の却下理由(完了課題で 1,000 件の上限に先に当たる)には当たらない。
  - ただ、取得の経路が増えて複雑になる。今回は見送り、200 を超えるスペースが出たときの次の手段として残す。
- **上限をなくす**: 呼び出し回数の最悪ケースを式で固定できなくなる(ADR 0006)。
- **既定の状態 ID(1〜3)を決め打ちして、上限外のプロジェクトを補う**: ADR 0012 に反する。
